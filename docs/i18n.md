# Frontend internationalisation (EN / IT)

The web UI is bilingual: English (default) and Italian. The rest of
the platform — code, REST API, DB schemas, OpenAPI docs, design docs,
audit log entries — stays English-only. Translation is **only** the
strings the end user reads on screen.

This document is the contract for adding or migrating UI strings.

---

## 1. Stack

| Piece | Choice | Why |
|---|---|---|
| Library | [`next-intl`](https://next-intl.dev) v4 | First-class App Router support, server + client components, no URL prefix needed |
| Locale source | `BVP_LOCALE` cookie, falls back to `Accept-Language`, then `en` | Cookie-only means no breaking URL changes for existing share links / bookmarks |
| Catalogue format | One JSON per locale: `frontend/messages/en.json`, `frontend/messages/it.json` | Plain JSON keeps the diff readable; nested namespaces group by feature |
| Toggle UI | `<LanguageSwitcher />` in the site header | Single `<select>`, writes the cookie, hard-reloads so server components re-render |

Wire-up files:

| File | Role |
|---|---|
| `frontend/src/i18n/request.ts` | `getRequestConfig` — reads cookie + headers, picks locale, imports the matching JSON |
| `frontend/next.config.mjs` | Wraps `nextConfig` with `createNextIntlPlugin("./src/i18n/request.ts")` |
| `frontend/src/app/layout.tsx` | Calls `getLocale()` + `getMessages()` and renders `<NextIntlClientProvider>` around the tree |
| `frontend/src/components/LanguageSwitcher.tsx` | Cookie-toggling `<select>` |
| `frontend/messages/en.json`, `it.json` | Translation catalogues, namespaced by feature |

## 2. Migration pattern (per file)

Every component or page that renders user-facing strings goes from
inline literals to keys looked up via `useTranslations`. The pattern
is the same everywhere; differences are only about *where* the hook
is called.

### 2.1 Client components (`"use client"`)

```tsx
"use client";

import { useTranslations } from "next-intl";

export default function ConsultationCard() {
  const t = useTranslations("consultation");
  return (
    <article>
      <h2>{t("title")}</h2>
      <button type="button">{t("openButton")}</button>
    </article>
  );
}
```

### 2.2 Server components (no `"use client"` directive)

```tsx
import { getTranslations } from "next-intl/server";

export default async function StudiesPage() {
  const t = await getTranslations("studies");
  return <h1>{t("heading")}</h1>;
}
```

### 2.3 Static-text fallbacks during Suspense

A `<Suspense fallback={...}>` cannot call hooks directly inside the
JSX expression because the fallback is evaluated outside the
component body. Wrap it in its own component:

```tsx
function FallbackMeta() {
  const t = useTranslations("common");
  return <p className="meta">{t("loading")}</p>;
}

<Suspense fallback={<div className="form"><FallbackMeta /></div>}>
  <RealForm />
</Suspense>;
```

The login page (`src/app/login/page.tsx`) is the canonical reference
for this pattern.

## 3. Catalogue conventions

`messages/en.json` is authoritative — every key must exist in
English. `messages/it.json` mirrors the same keys.

### 3.1 Namespaces

Group by feature. Reuse `common` for verbs / phrases shared across
many pages, otherwise create a feature-specific namespace.

```json
{
  "common": { "save": "Save", "cancel": "Cancel", ... },
  "site": { "studies": "Studies", "patients": "Patients", ... },
  "login": { "title": "Log in", "submit": "Log in", ... },
  "consultation": { "open": "Open consultation", ... }
}
```

A component that uses keys from `common.save` and `consultation.open`
calls `useTranslations("common")` and `useTranslations("consultation")`
twice (or scopes to the most-used namespace and qualifies the other:
`t.rich("namespace.key")`).

### 3.2 Naming

- Verbs in present infinitive (`"save"`, not `"saving"`).
- camelCase keys.
- Never embed sentences via concatenation — use ICU placeholders:

```json
{ "patientCount": "{n, plural, one {# patient} other {# patients}}" }
```

```tsx
t("patientCount", { n: 42 });  // -> "42 patients"
```

### 3.3 Adding a key

1. Edit `messages/en.json` — add the English string.
2. Edit `messages/it.json` — add the Italian translation under the
   same key path.
3. Replace the inline literal in the `.tsx` with `t("namespace.key")`.

A missing key in one locale logs a console warning and falls back to
the key path. Keep both files in lockstep.

## 4. Locale resolution at request time

`src/i18n/request.ts`:

```ts
async function resolveLocale(): Promise<AppLocale> {
  const cookieStore = await cookies();
  const fromCookie = cookieStore.get("BVP_LOCALE")?.value;
  if (isSupported(fromCookie)) return fromCookie;
  const hdr = (await headers()).get("accept-language") ?? "";
  const primary = hdr.split(",")[0]?.split("-")[0]?.toLowerCase();
  if (isSupported(primary)) return primary;
  return "en";  // safe default
}
```

The cookie is set by `LanguageSwitcher` for one year, `path=/`,
`samesite=lax`. There is **no URL prefix**. This is intentional:

- existing share links keep working;
- API routes are unaffected (they're locale-agnostic);
- SEO concerns are minimal (the platform is auth-gated).

If we later need search-engine-friendly locale URLs, switch to
`createMiddleware` from `next-intl/middleware` and add `/en/`,
`/it/` prefixes; the `getRequestConfig` already handles whatever the
caller resolves.

## 5. What stays English

These never get translated:

- **Code** (variable names, comments, log messages).
- **REST API** — endpoint paths, JSON keys, error codes returned in
  `{"detail": "..."}` (they're consumed by clients, not humans).
- **OpenAPI docs** at `/docs`.
- **DB schemas** — column names, enum values, table names, audit
  action verbs.
- **Audit log entries** (`action`, `resource_kind`, etc.).
- **Documentation under `docs/`**.
- **CHANGELOG**, README, DESIGN.

Translations live exclusively in `frontend/messages/*.json` and
exclusively render through `useTranslations` / `getTranslations`.

### How to claim a batch

1. Pick a batch above.
2. For each file, list the user-visible strings (titles, button
   labels, placeholders, aria labels, error messages).
3. Add them under a new namespace in `messages/en.json` AND
   `messages/it.json` simultaneously.
4. Replace the literals with `t("...")` calls (see §2).
5. Run `pnpm exec tsc --noEmit` and `pnpm exec next build` locally.
6. Commit with prefix `i18n: migrate <batch>`.

## 7. Pitfalls

- **`alt`, `title`, `aria-label`, `placeholder`** — easy to forget,
  also user-visible. Search for them when migrating a file.
- **String concatenation** — `${prefix} ${name}` patterns must move
  to ICU `{name}`-style placeholders, otherwise the translation can't
  reorder words.
- **Date / number formatting** — use `useFormatter()` from next-intl
  rather than hand-rolled `toLocaleString()` so the locale stays in
  sync with the catalogue.
- **Server components** — call `getTranslations`, not
  `useTranslations`. The lint rule will flag the wrong import once we
  add a custom rule, but for now follow the file's `"use client"`
  directive.
- **Missing keys** — `next-intl` falls back to the key path, so a
  forgotten key shows up as e.g. `consultation.openButton` in the UI.
  Grep both message files when wrapping up a batch.

## 8. Testing translations

Run the dev server and toggle the language from the header. The
`LanguageSwitcher` writes `BVP_LOCALE=it` and reloads — every page
re-renders against the IT catalogue. To force a locale headlessly:

```sh
curl -H 'Cookie: BVP_LOCALE=it' http://localhost:3000/login
```

Returns the Italian-rendered HTML for the login page.

For automated smoke coverage (future): a vitest pass that imports
both catalogues and checks key parity (every `en.json` key has a
matching `it.json` key, no orphan keys in `it.json`).
