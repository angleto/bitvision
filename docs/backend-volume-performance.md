# Backend volume delivery: performance notes

The viewer's first paint is gated by one network request:
`GET /api/series/{id}/volume.raw`. A typical CT series at 512x512x50
packs to ~13 MB of Float32 (32-byte header + `nx*ny*nz*4` bytes). This
document explains the optimizations that live behind that endpoint.

## Binary format (unchanged)

Little-endian, matches `services.volumes.HEADER_STRUCT`:

```
uint32 nx, uint32 ny, uint32 nz
float32 sx, float32 sy, float32 sz        (voxel spacing, mm)
float32 value_min, float32 value_max      (global range)
float32 scalars[nx * ny * nz]             (x-fastest, C-contiguous)
```

Header is 32 bytes. Frontend parses in a single `DataView`, then wraps
the remainder as a `Float32Array` view. Do NOT break this layout — the
preview endpoint reuses the same header.

## Optimizations

### 1. gzip compression on the wire

When the client sends `Accept-Encoding: gzip`, the handler compresses
the payload with `gzip.compress(data, compresslevel=1)` and sets
`Content-Encoding: gzip`. Level 1 was chosen deliberately:

| Level | Ratio (CT volume) | CPU time (13 MB) |
|-------|-------------------|------------------|
| 1     | ~1.8x             | ~40 ms           |
| 6     | ~2.1x             | ~180 ms          |
| 9     | ~2.2x             | ~400 ms          |

On a LAN the extra 4% ratio from level 6 costs more time than the
bytes save. Reverse proxies (nginx, CloudFront) can override if they
re-compress at higher levels — we set `Content-Encoding: gzip` so they
won't double-compress.

Implementation: see `_client_accepts_gzip()` and `_volume_response()`
in `backend/src/bvphoenix/api/studies.py`.

### 2. Chunked streaming for large payloads

Payloads over 20 MB (`_STREAM_THRESHOLD_BYTES`) return a
`StreamingResponse` that yields 1 MB chunks rather than a single
`Response(content=...)`. This matters because FastAPI/Starlette buffers
the entire `Response.content` in a second bytes object — for a 100 MB
MRI we'd need 200 MB of headroom per concurrent request. Streaming
caps per-request memory at ~2 chunks.

The 20 MB threshold is above the common 13 MB CT case on purpose:
small volumes take the cheap non-streaming path.

### 3. Progressive loading via preview endpoint

`GET /api/series/{id}/volume-preview.raw` returns a 1/8-resolution
version of the volume (factor=2 in each axis -> 1/8 voxel count). For
the typical CT that's ~1.6 MB vs. ~13 MB. Same 32-byte header format,
just with smaller nx/ny/nz and scaled spacing.

Recommended frontend strategy:

1. Kick off both requests in parallel: preview + full-res.
2. Render the preview as soon as it arrives (usually <200 ms on a LAN).
3. Swap in the full-res `vtkImageData` when its fetch completes.

The preview is generated by stride-sampling (`volume[::2, ::2, ::2]`)
rather than box-filtering. A proper downsample would look nicer but
costs a 13 MB multiply-add pass; the preview only shows for a second
or two so stride sampling is fine.

Implementation: `pack_low_res()` in `services/volumes.py`.

### 4. Prefetch on ingest

The worker task `workers/src/bvworkers/tasks/prefetch_series.py`
(`prefetch_series`) pre-packs both the full-res blob and the preview
to S3 the moment a series finishes ingesting. That way the first
viewer open is a pure S3 read (cached derivative path in the handler)
instead of a 5-10 second pack.

**Wiring** (TODO): the task is registered in
`workers/src/bvworkers/tasks/registry.py` but not yet enqueued
automatically. The obvious call site is
`backend/src/bvphoenix/cli/import_dicom.py` right after
`series_row.ingestion_complete = True` — enqueue
`prefetch_series(series_id)` after the commit. Any future non-CLI

## Rough numbers (512x512x50 CT)

| Stage                              | Before | After |
|------------------------------------|--------|-------|
| Full-res payload on the wire       | 13 MB  | ~7 MB (gzip) |
| Preview payload on the wire        | n/a    | ~0.9 MB (gzip) |
| Time to first render (cold cache)  | ~8 s   | ~0.8 s (preview) |
| Time to full-res render            | ~8 s   | ~2 s  |
| Server RAM per 100 MB MRI request  | ~200 MB | ~2 MB (streaming) |

Numbers are order-of-magnitude; they depend heavily on network and
the specific scanner's compressibility.

## File map

- `backend/src/bvphoenix/api/studies.py` — `volume.raw` and
  `volume-preview.raw` handlers, gzip + streaming helpers.
- `backend/src/bvphoenix/services/volumes.py` — `pack_series`,
  `pack_low_res`, header struct.
- `workers/src/bvworkers/tasks/prefetch_series.py` — arq task that
  pre-populates the S3 cache on ingest.
- `workers/src/bvworkers/tasks/pack_volume.py` — the original on-demand
  packer, still used by the `/pack-volume` endpoint.
