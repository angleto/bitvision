# bitvision phoenix: Design Document

Modern rewrite of the old DICOM search engine (bitvision, 2012-2015) as a
public web platform, open source (AGPL-3.0), with native LLM support and
a consent-first model for medical imaging data.

## 1. Base capabilities

- **User-driven DICOM upload**: patients, doctors and researchers upload
  their own studies (studies / series / instances / volumes). For the MVP,
  no automatic ingestion from hospital PACS (planned for the future as an
  additional client on the same upload API).
- **Admin-only crawler**: connectors for curated public archives (TCIA,
  OpenNeuro, Radiopaedia) to populate the demo library. Plugin
  architecture, admin-operated.
- **Per-study contribution tier** (T1 private, T2 controlled sharing,
  T3 anonymized opt-in, T4 public CC): chosen at upload,
  versioned consent, revocable.
- **Automatic indexing**: DICOM metadata parsing, generation of
  thumbnails / MPR / packed NIfTI volumes, computation of multimodal
  embeddings at upload time.
- **Search**: full-text on metadata, structured filters (modality,
  anatomy, tags), vector similarity search (image + text). **No
  ontologies**.
- **Advanced in-browser DICOM viewer**: 2D, multi-planar reconstruction
  (MPR), 3D volume rendering, annotation management.
- **Annotations**: manual (drawings, bounding boxes, segmentations, text)
  and automatic, generated by multimodal LLMs, always kept distinct in
  the data model (`source`, `model_id`, `confidence`, `reviewed_by_human`).
- **Virtual Organizations (VO)**: groups with roles (read / write /
  annotate / admin) for structured sharing between users.
- **Granular sharing**: patient to doctor, patient to organization,
  study to single user, dataset to commercial researcher
  (marketplace). Delegation OFF by default, anonymization for external
  grants ON by default.
- **Registered-only access (F12.2d)**: access to medical data,
  including public data (OpenData), always requires login.
  Registration unlocks read access to the OpenData dataset, upload,
  sharing, LLM, and marketplace. The only exceptions are
  `/api/auth/*`, `/healthz`, shared links (`/api/shared/*`) and the
  agent-to-agent protocol (`/api/a2a`) which uses the explicit
  `public_user` dep.
- **Health Record** (inspired by FSE 2.0):
  extended demographics, clinical documents (consents, discharges,
  prescriptions, lab reports, ER notes), unified chronological
  timeline, patient-level sharing. See docs/fascicolo.md.
- **LLMs as first-class citizens**:
  - auto-annotation of images / series / volumes
  - Q&A on a selected exam (RAG over report + annotations + metadata)
  - generation of textual descriptions and embeddings from images
  - tool-using agents via REST API + MCP server
- **REST API** with OpenAPI docs, designed to be *LLM-friendly* (tool
  use by external agents).
- **Native MCP server** (stdio + HTTP transports, ADR 0019; read +
  write tool families across every clinical surface — patients,
  studies, search, sharing, documents, care phases, segmentations,
  imaging, notifications, ...): any MCP client (Claude Desktop, IDE,
  agents) can query studies, patients, annotations, reports,
  similarity search, generate LLM descriptions, and write back tags /
  metadata / care phases / annotations / consultations under granular
  scopes. Detailed in §7.
- **A2A protocol (Agent-to-Agent)**: Agent Card for discovery +
  JSON-RPC 2.0 endpoint for task lifecycle. Autonomous doctor agents
  can delegate tasks (find similar cases, analyze images, generate
  report) and receive asynchronous results. See docs/agent-protocols.md.
- **Open source (AGPL-3.0)** and deployable via `docker compose up`.

## 2. Design principles (non-negotiable constraints)

- **Mission**: the system serves to improve health. Hardcoded deny
  list: no military use, surveillance, social scoring,
  insurance underwriting, employment decisions, discriminatory
  screening.
- **No ontologies**. Flat tags + vectors + DICOM metadata are sufficient.
- **Descriptors-first**: every indexed object has tags and at least one
  vector embedding.
- **Series is the logical unit**, not the file: volumetric DICOMs
  consist of hundreds of slices; upload, storage, embeddings and
  sharing are designed around the series.
- **Upload-driven** for the MVP (PACS connector planned for later, same
  generic ingestion API).
- **Consent first-class**: every upload picks a tier (T1-T4) with
  versioned, revocable consent.
- **Revocability**: all non-commercial grants are instantly revocable;
  only commercial marketplace grants (is_commercial = true) are
  irrevocable for contractual stability.
- **Anonymous-first on public data**: no wall between visitor and demo.
- **GDPR-native**: health data as a special category, optional EU
  residency, right to erasure implemented, k-anonymity >= 5 on
  aggregated T3 datasets.
- **Positioning "research / educational, not for primary diagnosis"**
  to stay outside MDR/CE as a medical device (to be reconsidered if
  and when certification is desired).
- **Provider-agnostic**: generic S3 API (boto3 + configurable
  endpoint), LLM behind a strategy pattern.
- **AGPL-3.0 + CLA**: the code is open; a SaaS fork must publish its
  modifications. CLA (to be set up before the first external PR)
  preserves the dual-license option.

**Auth**: local password + JWT signed with `BVP_JWT_SECRET` for
human users; per-assistant `client_id`/`client_secret` for AI/MCP

live in PostgreSQL; permissions enforced via RLS.

balancer; PostgreSQL in replica; S3 is naturally scalable; LLMs are
external calls; the viewer is server-static.

## 4. Data model (high level)

The Health Record is organised on three orthogonal axes plus one cross-cutting
dimension: **Storage axis (`Document`)**, **Temporal axis (`ClinicalEvent`
atomic, `CarePhase` grouping)**, **Organisational axis (`Folder`)**, and the
**cross-cutting `Tag`** (imaging-scoped). The conceptual model and decision
rules are in
[`data-model.md` §0](./docs/data-model.md#0-conceptual-overview-the-three-axis-model);
this section summarises the principal/resource/grant tables that sit
underneath those axes.

The detail of the permissions hierarchy is in
[authorization.md](./docs/authorization.md). Summary here:

**Principals (unified subjects):**
- `subjects`: base table for user/org/group/public
- `users`, `organizations`, `groups`: FK to `subjects`
- `memberships`: edges (user × org × role), (user × group × role),
  (group × org × 'nested')

**Resources:**
- `patients`: demographics (can be the user themselves or a patient
  managed by a doctor/organization)
- `studies`: DICOM exams, with `owner_subject_id`, `owner_org_id`,
  `contribution_tier ENUM('t1','t2','t3','t4')`, `is_public`,
  `is_listed_for_sale`, `ingestion_complete`
- `series`: DICOM series (1:N with instances); logical unit for sharing,
  annotations, LLM jobs, search results
- `instances`: individual DICOM images (point to S3 key)
- `derivatives`: thumbnail, MPR cache, packed NIfTI volume, tile
  pyramid (`series_id`, `kind`, `format`, `s3_key`, `generated_at`)
- `annotations`: on study / series / instance, with `source
  ('human'|'llm')`, `model_id`, `confidence`, `reviewed_by_human`
- `reports`: textual reports, versioned
- `tags`: flat (`namespace:value`) applicable to studies/series
- `embeddings`: `pgvector`, reference to resource + `model_id`
- `datasets`: curated collections of studies/series

**Authorization:**
- `grants`: atomic grants (grantor → grantee, permissions[],
  conditions, valid_from/until, parent_grant_id, is_commercial)
- `training_consents`: versioned consent for T3
  (`study_id`, `consent_version`, `consent_hash`, `granted_at`,
  `revoked_at`)

**Marketplace & billing:**
- `sale_listings`: public listings (seller, resource, price, license,
  conditions, active)
- `purchases`: transactions (`listing_id`, `buyer_subject_id`,
  `grant_id`, `paid_cents`, `paid_at`, `payment_ref`)
- `contributor_ledger`: credits for T3 contributors when a training
  license deal is closed
- `user_quotas`: storage usage vs free tier (only for T1/T2)
- `organization_plans`: org plan (free/pro/enterprise)

**Audit:**
- `audit_log`: every non-trivial action (view, download, llm run,
  share, revoke, transfer)

**Git-like versioning (F12, see `docs/versioning.md`):**
- `entity_objects`: immutable content-addressed blob (sha256 of the
  canonical RFC 8785 payload), one row per version of any clinical
  entity. Natural dedup between identical commits.
- `commits`: DAG anchor: `parent_hashes BYTEA[]`, `tree_hash`,
  author + AI provenance (author_kind, model_id, agent_token_id),
  message, db_txid forensic.
- `manifest_entries`: expanded (commit_hash × entity_kind × entity_id →
  object_hash), HASH-partitioned on 16 buckets for fast queries at
  any commit.
- `refs`: branch heads `(patient_id, ref_name) → commit_hash`. Only
  two valid names: `main` (always) and `consultation/<id>` (lifetime
  bound to the consultation that opened it).
- `ref_log`: append-only of every ref move (init/commit/
  merge/reset/revert/rebase/delete).
- `proposals`: pull request: source_ref → target_ref, status,
  reviewer, merge_commit. 1:1 with the consultation that generated it.
- `merge_conflicts`: pre-computed cache of conflict detection.
- `binary_blobs`: S3 indirection content-hash + refcount for large
  files (NIfTI segmentation, PDF) that do NOT live in entity_objects.

PLATFORM_OWNER subject (see 0036_platform_owner_subject) owns every
OpenData record; the visibility filter surfaces these patients to all
authenticated users with read-only enforced via permissions.

**RLS**: every SELECT goes through policies that combine ownership,
memberships, active grants, and the public flag. The application never
issues queries like `WHERE user_id = X`: the DB does the filtering.
See authorization.md §5. The 8 versioning tables have patient-scoped
RLS (commits/refs/ref_log/proposals direct via patient_id;
manifest_entries via JOIN to commits; entity_objects via JOIN to
manifest_entries).

**Production hardening (known gap, F12.7)**: Postgres bypasses RLS
for the *owner* role unless `FORCE ROW LEVEL SECURITY` is on. In dev
(`bvphoenix` is both owner and app role) RLS is decorative: the
app-layer predicates in `services/permissions.py` remain the only
effective gate. Deployment must pick between (A) an app role
distinct from owner [recommended], or (B) FORCE RLS in a new
migration with `set_config 'service'` at the top of every DML
migration. Structural xfail test in
`tests/test_versioning_security.py::TestRlsStructuralEnforcement`.
Details in [docs/security-rls.md §"Production hardening required"](./docs/security-rls.md).

## 5. Ingestion pipeline

**Logical unit: the series**, not the single file. A typical CT has
200-500 slices; the project treats the series as the atom of sharing,
annotation, embedding, and LLM operations.

1. **Client requests a presigned URL** from the backend (per series or per ZIP/folder)
2. **Client uploads directly to S3** the DICOM files via parallel S3
   multipart upload, with resume and progress
3. **Client notifies** the backend with the complete manifest (list of
   SOPInstanceUID, hash, byte count)
4. **Async worker** (Celery/Arq) processes the series:
   - `pydicom`: parse metadata, extract StudyInstanceUID,
     SeriesInstanceUID, SOPInstanceUID, modality, anatomy, etc.
   - Sort by `InstanceNumber` and `ImagePositionPatient`
   - Dedup on SOPInstanceUID
   - Integrity check (`expected_instance_count` vs received)
   - PHI de-identification (T3/T4 only): `pydicom-deid` for metadata,
     OCR + redaction for burned-in text in pixels
   - **Derivatives**:
     - series thumbnail (central slice)
     - MPR cache (sagittal, coronal)
     - packed NIfTI volume `.nii.gz` via `dcm2niix`, loadable from
       the viewer in a single GET instead of hundreds
     - tile pyramid for high-resolution 2D (mammo, WSI) where
       applicable
   - **Embeddings** (series-level by default; instance-level
     opt-in):
     - radiology multimodal: BiomedCLIP / MedCLIP
     - text on report (if present): text embedding
     - general-purpose fallback: Vertex multimodal
   - Writes metadata and embeddings to PostgreSQL + pgvector
   - `series.ingestion_complete = true`
5. **User notification** (WebSocket / polling): study ready, visible
   in the viewer

**Concrete Python stack:**
- `pydicom`: parsing & I/O, all SOP Classes
- `highdicom`: DICOM SR / Seg / ParametricMap for annotations saved
  as native structured DICOM (interop with other PACS)
- `pynetdicom` + `dicomweb-client`: prepared for the future PACS
  connector
- `SimpleITK` / `ITK`: registration, resampling, filtering
- `dcm2niix` (CLI, via subprocess): volume packing
- `nibabel`: NIfTI I/O on the Python side
- `MONAI` + `TorchIO`: 3D preprocessing and pre-trained models
  (in a dedicated worker, not in the API container)
- `pydicom-deid`: anonymization (mandatory for T3, opt-in for T2
  external grants)

## 5.5. Crawler component (admin-only)

Dedicated worker, separate from the API, to populate the public dataset
library from curated open archives. Not exposed to end users.

- **Plugin architecture**: one connector per source (TCIA, OpenNeuro,
  Cancer Imaging Archive, Radiopaedia, etc.). Each connector defines
  `discover()`, `download(study)`, `map_metadata()`.
- **Reuses the standard ingestion pipeline** (presigned S3 upload +
  parsing worker + embeddings). Does not bypass it.
- **Default tier**: T4 (public CC) for data from archives with an open
  license; never T3 without explicit consent from the dataset.
- **Mandatory provenance**: every crawled study saves `source_url`,
  `license`, `attribution`, `crawled_at`, `crawler_version`.
- **Respects** `robots.txt`, per-source rate limits, and dataset Terms
  of Use.
- **Schedulable** via cron / k8s CronJob for bootstrap and delta
  updates.
- **CLI**: `bvphoenix crawler run --source tcia --collection LIDC`.

## 6. Viewer

**OHIF v3** as the base (Cornerstone3D + VTK.js):
- ready, mature, used in clinical practice, FOSS MIT
- 2D / MPR / 3D volume rendering already implemented
- plugin system for adding custom annotation tools and LLM
  integration

Planned customizations:
- hybrid annotation panel (human + LLM with distinct badges)
- "annotate with LLM" button: async job, notification when ready
- "similar to this" panel: similarity search over the vector DB
- "ask the LLM" panel: contextual chat on the selected exam
- persistent banner "you are accessing the data of X under grant Y
  valid until Z" to make the chain of permissions visible (cf.
  authorization.md §7)

### 6.1 Sub-stack separation (mDIXON / multi-echo / DWI)

One DICOM `SeriesInstanceUID` can carry several co-located volumes: a
Philips mDIXON series interleaves Water / Fat / In-phase / Out-of-phase
stacks that share the same z-positions and `ImageOrientationPatient`.
Packed naively (sort all instances by z, stack), the contrasts interleave
at near-identical z, the slice spacing collapses to ~0 and the MPR
geometry is garbage.

`services.volumes.partition_substacks` de-interleaves them at volume-build
time, BEFORE the sort, in two layers:
1. **Tag compound key** (`series_splitter.substack_tag_key`): orientation,
   FrameOfReferenceUID, `ImageType[2]` (W/F/IP/OP), `EchoNumbers` +
   `EchoTime`, `DiffusionBValue`, Philips `StackID`, temporal position,
   acquisition number.
2. **Geometric duplicate-z fallback**: within a tag group, if a
   through-plane position (projected onto the slice normal) repeats K>1
   times, the i-th occurrence of each position is assigned to sub-stack i
   — so every emitted stack is monotonic-unique in z, the precondition the
   spacing/geometry math needs.

A single coherent series returns one stack (`main`, byte-identical pack —
no regression). The fix lives in the one place that builds the blob
(`pack_series`), so the prepack worker, the on-demand `volume.raw`
endpoint, EARL, segmentation/ROI and MCP are all corrected at once. The
DICOM series stays one DB `Series` (the DICOM invariant is preserved; no
re-ingest, saved `/viewer/series/<id>` links keep working).

Storage: `derivatives` gains a `stack_index` dimension (unique on
`series_id, kind, format, stack_index`); stack 0 is the primary
(largest; ties prefer Water) and aliases the canonical `volume.f32` key,
extra contrasts get `volume.stack-<N>.f32`. `volume.raw?stack=<N>` serves
a specific contrast; `display-metadata.sub_stacks[]` lists the available
stacks + labels so the viewer renders a contrast picker. Follow-up: persist
the discriminators at ingest (so display-metadata is a DB read, not a
header scan) and optionally promote sub-stacks to first-class taggable
series.

## 7. LLM layer

**Abstraction**: `LLMProvider` interface with `AnthropicProvider`,
`OpenAIProvider`, `VertexProvider`, `SelfHostedProvider`
implementations. Behind it, routing for:
- platform default model (for prepaid credits with ~20% markup)
- BYOK: if the user has configured their own key, calls use that
  key (zero cost for the platform)

**Default model**: Claude Opus 4.6 (more capable) or Sonnet 4.6 (more
economical) depending on the task. Every call is tagged with
`model_id` for reproducibility.

**Embedding models** (for similarity search and LLM grounding):
- **BiomedCLIP** (Microsoft): primary choice for radiology images
- **MedCLIP** / **RadFM**: radiology-tuned alternatives
- **Vertex multimodal-embedding-001**: general-purpose fallback
- swappable via config; every embedding is tagged with `model_id` for
  reproducibility

**Exposed functions:**
- `annotate_image(target_id, prompt_template) → annotations[]`
- `generate_report(study_id, template) → text`
- `embed_image(target_id) → vector`
- `embed_text(text) → vector`
- `qa(study_id, question) → answer` (RAG on report + annotations +
  metadata)

**MCP server** (implemented; the **source of truth** for the tool
catalogue is the directory listing of `mcp/src/bvmcp/tools/`, not a
fixed count repeated in this document). Tool families cover, at
minimum:

- **Search** (`search.py`, `search_advanced.py`): full-text, structured,
  similarity, semantic, hybrid (RRF), patient-scoped search.
- **Studies / series / images** (`studies.py`, `images.py`,
  `imaging.py`): study + series detail, thumbnails, MPR slice, DICOM
  metadata allowlist, ROI crop, measurements, SUV, segmentations,
  registrations.
- **Patients + fascicolo** (`patients.py`, `bundle.py`,
  `patient_writes.py`, `provenance.py`, `external_identifiers.py`):
  patient detail, fascicolo index/timeline/bundle, document list,
  contacts, external-id link, scope introspection.
- **Documents** (`documents.py`, `document_reads.py`,
  `document_writes.py`): list / get / update / merge / delete /
  restore / link-to-study / OCR text / entities.
- **Care phases / temporal axis** (`care_phases.py`,
  `clinical_events.py`, `clinical_event_attachments.py`): propose /
  apply / create / update / reorder / restore phases + clinical event
  CRUD + attachments.
- **Folders + tasks + notifications + calendar**
  (`folders.py`, `patient_tasks.py`, `notifications.py`,
  `calendar_subscriptions.py`): organisational axis, due-date tasks,
  outbound channels, ICS exports.
- **Annotations + tags + reports**
  (`annotations.py`, `tags.py`, `metadata_writes.py`,
  `clinical_notes.py`, `report_contents.py`, `segmentations.py`):
  read + write with per-tool scopes (`tags:write`,
  `studies:write_metadata`, ...).
- **Consultations + LLM actions** (`summaries.py`, `qna.py`, `help.py`):
  summarize, Q&A, contextual help.

The server is stateless; it delegates everything to the backend REST
API with the caller credentials. The HTTP transport (ADR 0019)
resolves a per-assistant bearer to the same `AgentAssistant` row that
gates the REST API, so every tool respects the same visibility rules
(grants + RLS + per-patient scope) as the frontend.

**A2A protocol** (implemented):
- **Agent Card** at `/.well-known/agent-card.json` declares the
  currently shipped skills (dicom-search, similarity-search,
  image-analysis, patient-fascicolo, radiology-consultation; plus
  planned `fascicolo-executive-summary`).
- **JSON-RPC 2.0 endpoint** at `/api/a2a`: methods `agent/sendMessage`,
  `agent/getTask`, `agent/listTasks`, `agent/cancelTask`,
  `agent/getAgentCard`.
- Task lifecycle: submitted → working → input-required → completed/failed.
- LLM-powered intent routing when `BVP_LLM_PROVIDER=anthropic` and
  `BVP_ANTHROPIC_API_KEY` are set, with keyword-heuristic fallback so
  `/api/a2a` never 500s on intent parsing.
- Task persistence: Redis-backed (`a2a:task:<id>`, 7-day TTL), with a
  transparent in-process fallback for tests and single-process dev.

See docs/agent-protocols.md for the detailed architecture.

## 11. Long-running jobs

Long-running operations (imports, exports, artifact generation, batch
transforms, anything likely to exceed ~1s) share a common contract:
progress visible to the client, retry deduplication, cross-session
recoverability, and a configurable per-user queue cap to bound the
DoS surface. This section defines the unified `Job` abstraction and
the policies that consumers MUST follow.

### 11.1 Why a unified abstraction

Snapshot 2026-04-29: the project has Arq + Redis (workers, 30 min
job timeout, max 10 concurrent slots), but each long op rolls its
own state. `derivatives` rows for `pack_volume`, `reindex_jobs`
counter for embedding reindex, `summaries` cache for LLM, no state
at all for ZIP exports (Health Record and GDPR), no progress polling
endpoint, no per-user cap, inconsistent retry semantics. The result
is uneven UX (sync-blocking exports lose work on disconnect),
duplicated retries on autotag, and a missing DoS guard. A single
`Job` abstraction with shared semantics removes that drift and makes
new long ops cheap to add correctly.

### 11.2 Lifecycle

States: `queued → running → succeeded | failed | cancelled`.
Terminal states keep the row until `expires_at` (default 7 days for
exports, 24h for cache derivatives, configurable per kind).

```
   client                     api                worker
     │ POST /api/jobs/<kind>    │                    │
     ├─────────────────────────▶│                    │
     │                          │ idempotency lookup │
     │                          │ queue cap check    │
     │                          │ insert / return    │
     │ 200 / 202 {job_id}       │                    │
     ◀──────────────────────────┤                    │
     │                          │ enqueue Arq task   │
     │                          ├───────────────────▶│
     │                          │   update progress  │
     │                          ◀────────────────────┤
     │ GET /api/jobs/{job_id}   │                    │
     ├─────────────────────────▶│                    │
     │ 200 {status, progress,   │                    │
     │       stage, result_uri} │                    │
     ◀──────────────────────────┤                    │
```

### 11.3 Schema

```sql
CREATE TABLE jobs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  kind TEXT NOT NULL,
  owner_subject_id UUID NOT NULL REFERENCES subjects(id) ON DELETE CASCADE,
  idempotency_key TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN
    ('queued','running','succeeded','failed','cancelled')),
  progress_total INT,
  progress_done INT NOT NULL DEFAULT 0,
  stage TEXT,
  input JSONB NOT NULL,
  result_uri TEXT,
  error JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  started_at TIMESTAMPTZ,
  finished_at TIMESTAMPTZ,
  expires_at TIMESTAMPTZ NOT NULL,
  arq_job_id TEXT
);

CREATE UNIQUE INDEX jobs_idem_active_uniq ON jobs (idempotency_key)
  WHERE status IN ('queued','running');
CREATE INDEX jobs_owner_active_idx ON jobs (owner_subject_id, status)
  WHERE status IN ('queued','running');
CREATE INDEX jobs_kind_status_idx ON jobs (kind, status);
CREATE INDEX jobs_expires_idx ON jobs (expires_at);
```

The partial unique index on `idempotency_key` for active states is
the deduplication primitive: enqueueing an identical key while one
is already queued or running returns the existing row instead of
creating a new one.

### 11.4 Idempotency

The idempotency key is computed deterministically from:

- `kind` (operation type)
- `scope_ids` (e.g., `patient_id`, `study_id`, set ordered)
- `canonical_input` (JSON canonical form of the input payload, after
  scrubbing user-irrelevant fields)
- `owner_subject_id` (a different user repeating the same action gets a
  different job; results are not shared across users)

Same key with an active job in DB → return existing job, no new
work, HTTP 200. Same key with only terminal jobs → create a new job
(the user explicitly retried after completion, e.g., to refresh an
expired result).

### 11.5 Queue cap and DoS protection

Enforced at enqueue time, configurable via env / settings.

| Setting | Default | Purpose |
|---|---|---|
| `JOB_MAX_ACTIVE_PER_USER` | 20 | Hard cap on `(queued + running)` per user across all kinds. Primary DoS guard |
| `JOB_MAX_ACTIVE_PER_USER_KIND` | (unset) | Optional per-kind override map, e.g. `{"fascicolo_export": 3}` |
| `JOB_MAX_ACTIVE_GLOBAL` | 200 | Soft global cap; over the limit only admins may enqueue |
| `JOB_ADMIN_BYPASS_CAP` | true | Admins bypass per-user cap |
| `JOB_DEFAULT_EXPIRES_HOURS` | 168 (7d) | Result TTL; per-kind override map allowed |

Order of checks at enqueue:

1. **Idempotency lookup**. If an active job with the same key
   exists, return it without consuming cap.
2. **Per-user cap**: `COUNT(*) FROM jobs WHERE owner_subject_id = $1
   AND status IN ('queued','running')`. If `>=` limit, return HTTP
   `429 Too Many Requests` with a `Retry-After` hint.
3. **Per-kind override** if configured for the kind.
4. **Global cap** (advisory): if exceeded and user is not admin,
   return `429`.
5. Insert the row, enqueue the Arq task.

Idempotency dedup happens before the cap check, so retrying the same
operation never moves the user closer to the limit.

### 11.6 Progress, recovery, results

- **Progress** is updated in transactions by the worker every N
  steps (pattern already used by `reindex_jobs`). `progress_total`
  may be unknown initially and set later when a count is computed.
- **Stage** carries a short label (`'packing'`, `'uploading'`,
  `'extracting'`) for UI use.
- **Recovery on disconnect** is automatic: workers run independent
  of the client. Frontend persists active job ids per user
  (server-side via `GET /api/jobs?owner=me&active=true`, plus a
  `localStorage` fallback); on reload the panel re-attaches and
  resumes polling.
- **Results** for big artifacts (export ZIPs, packed volumes) go to
  S3 with a presigned URL in `result_uri`. Small results (text,
  JSON) may be inlined or served via `GET /api/jobs/{id}/result`.
- **Crash safety**: at worker startup, `running` jobs older than a
  stale threshold are reclaimed. Each consumer documents whether it
  re-runs from scratch or from the last committed checkpoint
  without side-effect duplication. Lacking that contract, a job is
  not safe to migrate to this abstraction.
- **Cleanup**: a periodic worker prunes rows past `expires_at` and
  deletes their S3 artifacts.

### 11.7 Endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/jobs/{kind}` | Enqueue or return existing. Body = canonical input. Returns `{job_id, status, idempotency_key}` |
| GET | `/api/jobs/{id}` | Status snapshot |
| GET | `/api/jobs?owner=me&active=true&kind=...` | List active jobs for the caller |
| DELETE | `/api/jobs/{id}` | Request cancellation (transitions to `cancelled` at next worker checkpoint) |
| GET | `/api/jobs/{id}/result` | Stream small inlined result, where applicable |

`POST` returns:

- `200 OK` if an active matching job already exists (dedup hit)
- `202 Accepted` on new enqueue
- `429 Too Many Requests` on cap exceeded, with `Retry-After`
- `400` on invalid input

### 11.8 Frontend contract

- Hook `useJob(jobId)` polls `GET /api/jobs/{id}` with exponential
  backoff (1s, 2s, 4s, capped at ~15s) until terminal state.
- Hook `useActiveJobs()` polls the active list at low frequency
  (e.g., every 30s) for the global "operations in progress" panel.
- `localStorage` persists the last N active job ids per user, so a
  reload before the server-side list fetches still surfaces them.
- Toast on terminal state with link to result (download,
  navigation, etc.).
- Cancel button issues `DELETE /api/jobs/{id}`.

### 11.9 Migration plan

1. **Schema + service + generic endpoints** (11.3, 11.4, 11.5, 11.7).
   Done.
2. **Migrate Health Record ZIP export** from sync route to Job consumer.
   Worker writes ZIP to S3, ``result_uri`` is the canonical
   ``s3://bucket/key`` pointer; the API re-signs a fresh presigned
   GET URL on every read of the parent Job. Audit log emission
   preserved. Done; legacy GET removed once the frontend cut over.
3. **Migrate GDPR ZIP export** (mirror of step 2). Done; legacy GET
   removed.
4. **Frontend ``useJob`` + active jobs panel**. Done. Hook polls with
   exponential backoff (1s → 15s cap) and stops on terminal state.
   ``ActiveJobsPanel`` in the site header polls the active list at

5. **Retrofit existing async ops** as Job consumers (opportunistic;
   see 11.10). Not pursued: the existing consumers (``pack_volume``,
   ``summary``, ``reindex_jobs``, ``deidentify_reindex_study``)
   already satisfy the contract via their own state tables and
   don't surface user-facing progress that would benefit from the
   shared abstraction. Revisit if a new consumer needs the same
   plumbing or if cleanup of the per-op tables becomes desirable.
6. **Periodic cleanup worker** for expired rows + their S3
   artifacts. Done. ``cleanup_expired_jobs`` runs hourly via Arq
   ``cron``; reads ``result_uri``, drops the S3 object best-effort,

### 11.10 Out of scope (intentional)

- **SSE / WebSocket for live progress**: polling is sufficient for
  foreground UX; streaming is a later optimization.
- **Cross-cluster job persistence**: Arq + Redis suffice in a
  single-region deploy; multi-region is in §10.4.
- **Resource quotas beyond count**: byte-size or CPU-time budgets
  per user are deferred until a misuse pattern emerges.
- **Backwards compatibility with existing per-op state tables**:
  retrofits in 11.9 step 5 are opportunistic; ops that already
  satisfy the contract via their own state may stay as-is, but new
  long ops MUST use this abstraction.

### 11.11 Resumable uploads (chunked session API)

The legacy ``POST /api/upload/bulk`` staged the entire multipart body to
S3 inside a single request: a disconnect anywhere before the ``202``
orphaned the staged bytes and lost the upload (the "don't close the
page" window). Uploads are now a durable, resumable **session** whose
handle exists from byte zero.

**Lifecycle** (``upload_sessions`` + ``upload_session_files``, migration
0017):

1. ``POST /api/upload/sessions`` — declare the manifest (per file:
   filename, relative_path, size, optional sha256) + tier / patient /
   folder / ISO flags. Creates the row in status ``awaiting_bytes`` and
   returns the session id, the **server-authoritative** ``chunk_size``
   (8 MiB), and per-file ``received_offset`` (0 fresh). No bytes yet.
2. ``PATCH /api/upload/sessions/{sid}/files/{idx}`` — one chunk per call,
   carrying ``Upload-Offset`` + the raw bytes. Each chunk is one S3
   multipart upload-part (PartNumber = offset / chunk_size + 1); every
   chunk except a file's last must be exactly ``chunk_size``. Idempotent
   on the offset: a re-sent already-acked chunk is a no-op; a gap returns
   ``409 {code:"offset_mismatch", expected_offset}`` so the client
   re-syncs. When ``received_offset == declared_size`` the multipart
   upload is completed and the file flips to ``staged``.
3. ``POST /api/upload/sessions/{sid}/commit`` — once every file is staged,
   builds the SAME ``canonical_input`` manifest the legacy endpoint built
   (pointing at the staged keys) and hands off to the UNCHANGED
   ``jobs_service.enqueue_or_get`` + ``ingest_bulk_files`` worker (§11).
   Idempotent: a re-commit returns the already-linked job.
4. ``GET /api/upload/sessions/{sid}`` — read live per-file offsets (resume).
   ``DELETE`` — abort (release multipart + delete staged).

**Storage isolation**: all bytes flow THROUGH the backend (no presigned
PUT); the client / MCP only ever see the session id + offsets, never an
S3 key or bucket.

**Frontend** (``UniversalUploader`` + ``uploadSessionStorage``): the
session id + file manifest are persisted to ``localStorage`` BEFORE the
first chunk. Progress is byte-based (sum of ``received_offset`` /
declared total), so a resumed upload starts at its true fill. On reopen
after a crash the File handles are gone, so the user re-selects the same
files (matched to slots by filename + relative_path + size) and only the
un-acked tail re-uploads. Post-commit, the existing ``useJob`` polling
(jobsStorage) takes over unchanged.

**GC** (``cleanup_upload_sessions`` cron, ~hourly): non-committed sessions
idle past ``STALE_WINDOW`` (1h on ``updated_at`` — ``append_chunk`` bumps
it, so active uploads never look stale) or past ``expires_at`` are
swept: each open multipart upload is aborted + staged objects deleted
(``abort_session``), then the rows dropped (CASCADE). This releases
incomplete parts in minutes rather than waiting for the bucket's
``AbortIncompleteMultipartUpload`` lifecycle rule (the belt-and-suspenders
backstop).

**MCP parity** (GUI-superset rule): ``create_upload_session`` /
``upload_session_chunk`` (base64 body) / ``get_upload_session`` /
``commit_upload_session`` / ``abort_upload_session`` under the
``documents:ingest`` scope. The base64 chunk tool is for small documents;
multi-GB imaging belongs in the web uploader / ``bvphoenix-import`` CLI.

ISO members are expanded client-side before the manifest is built; ZIP
server-side unpack-at-commit is a tracked follow-up (Phase 1 stages plain
files; the legacy ``/api/upload/bulk`` remains for ZIP-heavy uploads
during the transition).
